# Core Game Pillars Document

> **Purpose:** Define the fundamental design pillars that establish a game's identity, intended player experience, and development priorities. Core pillars provide a shared reference for making design decisions, evaluating features, managing scope, and maintaining a consistent gameplay experience.
>
> **Usage:** Copy this template into the game project's design documentation directory and customize it for that project. Define a small number of meaningful pillars that represent what makes the game distinctive. Avoid using generic qualities that could describe almost any game.

## 1.1 Document Purpose

This document defines the core design pillars of **[Game Name]**.

These pillars establish the essential qualities that the game must consistently deliver to fulfill its creative vision and intended player experience.

They guide:

- Gameplay and mechanic design.
- Narrative and worldbuilding decisions.
- Level and encounter design.
- Progression and reward systems.
- Art and audio direction.
- User experience and interface decisions.
- Feature prioritization and scope management.
- Evaluation of proposed changes.
- AI-assisted design and development.

## 1.2 Scope

This document defines the game's specific design priorities and identity.

It does not replace:

- Game vision and high-concept documentation.
- General game design principles.
- Core loop documentation.
- Gameplay and mechanic specifications.
- Art and audio direction documents.
- Production plans and priorities.

## 1.3 Document Authority

The approved core pillars are an authoritative reference for evaluating design decisions.

When a proposed feature conflicts with an established pillar:

1. Identify the conflict.
2. Evaluate the feature's value and impact.
3. Consider whether the feature can be redesigned to support the pillars.
4. If the conflict is intentional, document the reasoning.
5. Obtain project owner approval before changing an established pillar.

# 5. Pillar Prioritization

## 5.1 Priority Classification

Define the relative importance of the pillars.

| Priority | Meaning |
|---|---|
| Primary | Fundamental to the game's identity. Significant compromise requires careful evaluation and project owner approval. |
| Supporting | Strengthens the intended experience and helps deliver the primary pillars. |
| Optional | Desirable when resources and scope permit, but not essential to the game's identity. |

Optional design goals should not be treated as core pillars merely because they are desirable.

1. Identify the affected pillars.

3. Evaluate the impact on the intended player experience.

Before approving a significant feature, evaluate:

- Which pillar or pillars does it support?
- What player experience does it improve?
- Does it reinforce the game's identity?
- Does it introduce conflicts with existing pillars?
- Is it necessary to deliver the intended experience?
- Does its development cost justify its contribution?
- Could the same outcome be achieved with a simpler solution?

## 6.3 Misaligned Features

Features that do not support any pillar should be evaluated carefully.

Possible decisions:

- Remove the feature.
- Simplify the feature.
- Redesign it to support an existing pillar.
- Justify it as a necessary supporting feature.
- Defer it until its value is clearer.

Not every supporting feature must directly express a pillar. Technical infrastructure, accessibility requirements, and quality improvements may be necessary without directly creating a player-facing experience.

# 7. Scope and Development Priorities

## 7.1 Scope Protection

The core pillars should help prevent unnecessary feature expansion.

When considering new features, prioritize those that:

- Strengthen the game's identity.
- Improve the core gameplay experience.
- Support important player motivations.
- Reinforce multiple pillars without excessive complexity.
- Address a validated problem or opportunity.

Avoid adding features solely because they are common in the genre or appear attractive in isolation.

# 9. Pillar Maintenance

## 9.1 Review Triggers

Review the pillars when:

- The game concept changes significantly.
- The core gameplay loop changes.
- A major feature conflicts with the established design direction.
- Playtesting reveals that an intended experience is not being delivered.
- The target audience or intended experience changes.
- Production constraints require significant compromises.
- The project moves into a new major development phase.

## 9.2 Pillar Changes

Changes to the core pillars may fundamentally affect the game's identity and should be treated as significant design decisions.

# 10. AI-Assisted Design and Development

AI tools may support brainstorming, feature evaluation, design documentation, prototyping, and implementation planning.

AI-assisted work must follow these requirements:

1. Treat the approved core pillars as authoritative project design constraints.
2. Evaluate proposed features against relevant pillars.
3. Explain which pillars a proposed feature supports or potentially conflicts with.
4. Distinguish approved design decisions from suggestions.
5. Do not invent or redefine the game's pillars.
6. Do not modify pillar priority or definitions without project owner approval.
7. Avoid recommending features solely because they are common in other games.
8. Identify assumptions that require prototyping or playtesting.
9. Do not claim a pillar has been validated without supporting evidence.
10. Keep pillar definitions consistent across project documentation.

## 10.1 AI Feature Evaluation Reference

When asking an AI agent to evaluate a feature, provide:

- This core pillars document.
- The relevant core gameplay loop.
- Relevant gameplay and mechanic specifications.
- The proposed feature description.
- Known design constraints.
- Current validation evidence.

The AI agent should return:

- Supporting pillars.
- Potential pillar conflicts.
- Expected player experience impact.
- Scope and implementation implications.
- Alternative approaches.
- Unresolved assumptions.
- A recommendation with supporting reasoning.

The project owner retains final decision authority.
