# Project Lifecycle

## 1. Purpose

This document defines the production lifecycle used to organize, manage, and evaluate individual game projects.

It establishes:

- The major stages of a game project.
- The objectives of each stage.
- Expected activities and deliverables.
- Criteria for progressing between stages.
- Production planning and review practices.
- Project lifecycle management responsibilities.
- Guidelines for adapting the lifecycle to different project sizes and development approaches.

The lifecycle provides a structured framework for moving a game project from an initial concept to a released product while maintaining flexibility for experimentation and iteration.

## 2. Scope

These guidelines apply to game projects developed within the studio.

They cover the overall project lifecycle, including:

- Project initiation.
- Concept development.
- Pre-production.
- Prototyping.
- Production.
- Alpha.
- Beta.
- Release preparation.
- Release.
- Post-release support.

The lifecycle applies to different game genres, platforms, team sizes, and development approaches.

Individual projects MAY combine, extend, repeat, or omit stages when justified by their scope and development model.

## 3. Lifecycle Principles

### 3.1. Outcome-Oriented Development

Each lifecycle stage MUST have clear objectives and expected outcomes.

Progress SHOULD be evaluated based on demonstrated results rather than activity alone.

### 3.2. Iterative Development

Game development is inherently iterative.

Design, implementation, testing, and refinement SHOULD occur continuously rather than being treated as isolated activities.

### 3.3. Early Validation

Important assumptions and risks SHOULD be validated as early as practical.

Prototypes, technical experiments, and playable builds SHOULD be used to reduce uncertainty before committing to substantial production work.

### 3.4. Controlled Scope

Project scope SHOULD reflect available resources, technical capabilities, and development capacity.

New features and changes MUST be evaluated against their expected value and impact.

### 3.5. Quality Throughout Development

Quality MUST be considered throughout the lifecycle.

Testing, code review, performance validation, asset review, and documentation SHOULD be integrated into normal development activities.

### 3.6. Evidence-Based Decisions

Important lifecycle decisions SHOULD be supported by:

- Playable builds.
- Working prototypes.
- Test results.
- Technical evaluations.
- Player feedback.
- Production records.
- Documented risks and assumptions.

### 3.7. Adaptability

The lifecycle SHOULD provide structure without introducing unnecessary bureaucracy.

Projects MAY adjust their stages and review practices according to their complexity and risk.

## 4. Project Lifecycle Overview

The recommended lifecycle consists of the following stages:

1. Project Initiation.
2. Concept Development.
3. Pre-production.
4. Prototyping and Validation.
5. Production.
6. Alpha.
7. Beta.
8. Release Candidate.
9. Release.
10. Post-release.

These stages represent the project's overall progression.

They do not require every feature to follow a strictly sequential process. Individual features MAY move through their own design, implementation, testing, and refinement cycles within the broader project lifecycle.

## 5. Stage 1: Project Initiation

### 5.1. Objective

Establish the project, its ownership, initial purpose, and development context.

### 5.2. Key Activities

- Identify the initial project opportunity or idea.
- Define the project's preliminary purpose.
- Identify the intended platform or platforms, when known.
- Establish project ownership.
- Create the initial repository and development environment.
- Establish initial version control and collaboration practices.
- Identify major constraints and uncertainties.
- Determine whether further concept development is justified.

### 5.3. Expected Deliverables

Depending on project needs:

- Initial project description.
- Preliminary project objectives.
- Initial repository.
- Development environment.
- Initial project documentation structure.
- Initial list of assumptions and risks.

### 5.4. Exit Criteria

The project MAY proceed to concept development when:

- A clear project purpose exists.
- Project ownership is established.
- The initial development environment is available.
- The project has sufficient direction to investigate its concept.

Formal approval of a complete game design is not required at this stage.

## 6. Stage 2: Concept Development

### 6.1. Objective

Define the game's identity, intended player experience, and initial design direction.

### 6.2. Key Activities

- Define the core game concept.
- Identify the intended audience.
- Establish the game's genre and identity.
- Describe the intended player experience.
- Identify the primary gameplay activities.
- Develop an initial core loop.
- Identify major gameplay systems.
- Explore visual and audio direction.
- Identify potential technical challenges.
- Evaluate the concept's feasibility.
- Establish preliminary scope boundaries.

### 6.3. Expected Deliverables

Depending on project needs:

- Game concept document.
- Initial game vision.
- Target audience description.
- Core loop description.
- Preliminary feature list.
- Initial visual and audio direction.
- Initial risk assessment.
- Preliminary scope definition.

### 6.4. Exit Criteria

The project MAY proceed to pre-production when:

- The concept has a recognizable identity.
- The intended player experience is sufficiently clear.
- The primary gameplay direction is understood.
- Major assumptions and risks are identified.
- The concept appears feasible enough to justify further investigation.

The concept MAY be revised or abandoned when evidence indicates that its direction is unsuitable.

## 7. Stage 3: Pre-production

### 7.1. Objective

Prepare the project for implementation by defining its initial design, technical approach, production scope, and validation strategy.

### 7.2. Key Activities

#### Game Design

- Expand the core gameplay concept.
- Define important mechanics and systems.
- Identify progression and reward structures.
- Establish preliminary balancing principles.
- Define important player interactions.
- Identify initial content requirements.

#### Technical Planning

- Select the initial engine and development tools.
- Define the project architecture.
- Establish project structure.
- Identify technical dependencies.
- Evaluate major technical risks.
- Define initial performance considerations.
- Identify persistence and data requirements.

#### Art and Audio Planning

- Establish visual direction.
- Identify asset categories and production requirements.
- Define preliminary art and audio pipelines.
- Identify external asset dependencies.
- Establish licensing and attribution requirements.

#### Production Planning

- Define initial milestones.
- Establish a preliminary backlog.
- Identify dependencies and risks.
- Estimate initial development effort.
- Define validation and testing expectations.
- Identify major production constraints.

### 7.3. Expected Deliverables

Depending on project complexity:

- Game design documentation.
- Technical architecture documentation.
- Initial architecture decisions.
- Project structure.
- Initial feature backlog.
- Milestone plan.
- Art and audio direction.
- Asset requirements.
- Initial QA strategy.
- Risk assessment.

### 7.4. Exit Criteria

The project MAY proceed to prototyping when:

- The initial architecture is sufficiently defined.
- Major gameplay systems have an initial design.
- The project has a manageable initial scope.
- Important technical risks are understood.
- The development environment is functional.
- The team or project owner can begin validating the concept through implementation.

Not every system needs a complete specification before prototyping.

## 8. Stage 4: Prototyping and Validation

### 8.1. Objective

Validate the most important gameplay, technical, and production assumptions through experiments and playable prototypes.

### 8.2. Key Activities

- Implement the core gameplay loop.
- Prototype critical mechanics.
- Test interaction models.
- Validate important technical assumptions.
- Experiment with alternative implementations.
- Evaluate basic player feedback.
- Identify performance constraints.
- Test critical integrations.
- Refine or reject unsuitable design approaches.
- Update project risks and scope.

### 8.3. Prototype Types

Projects MAY use different prototype types.

**Gameplay prototypes**

Validate whether mechanics and interactions create the intended experience.

**Technical prototypes**

Validate engine capabilities, architecture, performance, and integration approaches.

**Visual prototypes**

Explore art direction, presentation, readability, and asset integration.

**Audio prototypes**

Explore sound identity, music direction, feedback, and audio implementation.

**Production prototypes**

Validate workflows, tools, automation, and content production approaches.

### 8.4. Expected Deliverables

Depending on project needs:

- Playable prototypes.
- Technical experiments.
- Validated gameplay mechanics.
- Prototype test results.
- Updated design documentation.
- Updated architecture decisions.
- Revised risk assessment.
- Updated production estimates.

### 8.5. Exit Criteria

The project MAY proceed to full production when:

- The core gameplay direction has been sufficiently validated.
- Critical technical risks have been addressed or have acceptable mitigation plans.
- The intended player experience appears achievable.
- The project scope is sufficiently understood.
- The development approach is viable.
- The project owner decides that further production investment is justified.

A prototype does not need production-quality assets or complete content.

If critical assumptions fail validation, the project SHOULD revise its concept, repeat prototyping, reduce scope, or stop development.

## 9. Stage 5: Production

### 9.1. Objective

Build the game's features, content, systems, and supporting infrastructure into an integrated and playable product.

### 9.2. Key Activities

#### Feature Development

- Implement planned gameplay features.
- Develop supporting systems.
- Integrate features incrementally.
- Maintain feature boundaries.
- Review architectural decisions.
- Validate implemented behavior.

#### Content Production

- Produce visual assets.
- Produce audio assets.
- Develop levels and environments.
- Create gameplay content.
- Integrate and validate content in the engine.

#### Quality Activities

- Perform automated and manual testing.
- Conduct code reviews.
- Validate asset quality.
- Identify and resolve defects.
- Monitor performance.
- Perform regression testing.

#### Production Management

- Maintain the project backlog.
- Track milestones.
- Manage dependencies.
- Monitor risks.
- Review scope and priorities.
- Update project documentation.
- Evaluate development progress.

### 9.3. Development Approach

Production SHOULD be organized into manageable iterations.

A project MAY use Scrum, Kanban, milestone-driven development, or another suitable approach.

Regardless of methodology:

- Work items SHOULD have clear objectives and acceptance criteria.
- Features SHOULD be integrated incrementally.
- Significant changes SHOULD be reviewed.
- Testing SHOULD occur continuously.
- Progress SHOULD be evaluated using demonstrable outcomes.

### 9.4. Expected Deliverables

Depending on the project:

- Implemented gameplay features.
- Integrated game systems.
- Production assets.
- Playable builds.
- Automated tests.
- Updated documentation.
- Completed milestones.
- Defect and validation records.

### 9.5. Exit Criteria

The project MAY transition to Alpha when:

- All planned core gameplay systems are implemented.
- The main gameplay experience is available from beginning to end, even if incomplete or unpolished.
- Major content and progression structures are integrated.
- The game is sufficiently stable for broader internal validation.
- Critical functionality is operational.
- Remaining work is understood and tracked.

Production does not end permanently when Alpha begins. Further development and refinement MAY continue during Alpha and Beta.

## 10. Stage 6: Alpha

### 10.1. Objective

Establish a complete or substantially complete gameplay experience and identify major functional, technical, and content problems.

### 10.2. Key Activities

- Validate the complete gameplay experience.
- Test progression from beginning to end.
- Identify missing or incomplete content.
- Resolve critical gameplay defects.
- Evaluate game balance.
- Validate save and loading behavior.
- Identify performance bottlenecks.
- Review usability and accessibility.
- Conduct internal playtesting.
- Refine the player experience.

### 10.3. Alpha Expectations

An Alpha build SHOULD:

- Be playable.
- Contain the essential gameplay systems.
- Support the intended primary game loop.
- Include the main progression structure.
- Allow meaningful end-to-end testing.
- Have known issues documented.

Alpha builds MAY contain:

- Placeholder assets.
- Incomplete content.
- Temporary UI.
- Unbalanced mechanics.
- Performance problems.
- Known defects.

These limitations MUST be understood and tracked.

### 10.4. Expected Deliverables

- Alpha build.
- Functional validation results.
- Updated defect backlog.
- Playtest findings.
- Updated performance assessment.
- Updated content completion status.
- Updated production priorities.

### 10.5. Exit Criteria

The project MAY proceed to Beta when:

- The complete primary gameplay experience is playable.
- Critical progression and gameplay paths function.
- Critical defects have been resolved or have accepted mitigation.
- Remaining content gaps are understood.
- The game is stable enough for broader testing.
- A realistic Beta stabilization plan exists.

## 11. Stage 7: Beta

### 11.1. Objective

Stabilize and refine the game while validating its quality, usability, performance, and compatibility.

### 11.2. Key Activities

- Resolve high-priority defects.
- Refine gameplay balance.
- Improve usability.
- Finalize remaining content.
- Validate save compatibility.
- Conduct regression testing.
- Test supported platforms and configurations.
- Optimize performance.
- Validate accessibility requirements.
- Review audio and visual consistency.
- Perform broader playtesting when appropriate.
- Reduce unnecessary scope changes.

### 11.3. Beta Expectations

A Beta build SHOULD:

- Contain substantially complete content.
- Provide a complete primary gameplay experience.
- Have stable core systems.
- Support meaningful regression testing.
- Have a manageable defect backlog.
- Reflect the intended final player experience.

Beta MAY still contain defects and require balancing or refinement.

### 11.4. Expected Deliverables

- Beta build.
- Updated test results.
- Updated defect records.
- Performance validation.
- Compatibility results.
- Updated release requirements.
- Release preparation checklist.

### 11.5. Exit Criteria

The project MAY proceed to Release Candidate preparation when:

- Required content is complete.
- Critical and high-priority defects have been addressed or explicitly accepted.
- Major gameplay systems are stable.
- Performance targets are sufficiently satisfied.
- Supported platforms have been validated.
- Release requirements are understood.
- No known unresolved issue makes release unacceptable.

## 12. Stage 8: Release Candidate

### 12.1. Objective

Validate a build that is intended to become the released product.

### 12.2. Key Activities

- Freeze nonessential feature development.
- Generate release builds.
- Validate release configurations.
- Perform final regression testing.
- Validate installation and startup.
- Verify save and loading behavior.
- Validate platform-specific requirements.
- Review user-facing content.
- Verify credits, licenses, and attributions.
- Review release documentation.
- Resolve release-blocking defects.

### 12.3. Release Candidate Expectations

A Release Candidate SHOULD:

- Contain the intended release content.
- Use release configuration.
- Be reproducible from the intended source revision and build process.
- Pass required release validation.
- Have no known release-blocking defects.
- Have its version and build information recorded.

Only necessary fixes SHOULD be introduced during this stage.

### 12.4. Expected Deliverables

- Release Candidate build.
- Release validation results.
- Final defect assessment.
- Release notes draft.
- Verified credits and attributions.
- Release package.
- Release readiness assessment.

### 12.5. Exit Criteria

A Release Candidate MAY be approved for release when:

- Required validation has passed.
- No unresolved release-blocking issue remains.
- Release assets and documentation are ready.
- Platform requirements are satisfied.
- The project owner approves release.

If significant defects are discovered, the project SHOULD return to an appropriate development or stabilization stage and produce another candidate.

## 13. Stage 9: Release

### 13.1. Objective

Deliver the approved game build to its intended audience.

### 13.2. Key Activities

- Publish the approved build.
- Verify the published package.
- Validate installation and startup where practical.
- Publish release notes.
- Publish required credits and attribution information.
- Monitor release health.
- Record the released version.
- Preserve release artifacts.
- Communicate known issues when necessary.

### 13.3. Release Requirements

Before release:

- The project owner MUST approve the release.
- The released build MUST correspond to the approved source revision.
- Required platform and distribution requirements MUST be satisfied.
- Known critical issues MUST be resolved or explicitly accepted.
- Required licenses and attributions MUST be included.
- Release artifacts MUST be preserved.

### 13.4. Expected Deliverables

- Published game build.
- Release notes.
- Version information.
- Release records.
- Preserved build artifacts.
- Known issue information, when applicable.

### 13.5. Exit Criteria

The project MAY transition to post-release when:

- The intended release has been published.
- The published build has been verified where practical.
- Release records are preserved.
- Initial release issues are understood and tracked.

## 14. Stage 10: Post-release

### 14.1. Objective

Maintain the released product, evaluate its performance, and determine appropriate future improvements.

### 14.2. Key Activities

- Monitor reported defects.
- Investigate technical incidents.
- Provide patches and fixes.
- Evaluate player feedback.
- Monitor performance and compatibility issues.
- Maintain supported platforms.
- Evaluate requested improvements.
- Plan updates or additional content when justified.
- Review development outcomes.
- Conduct a project or release postmortem.

### 14.3. Post-release Work Categories

Post-release activities MAY include:

**Maintenance**

- Critical fixes.
- Compatibility updates.
- Stability improvements.
- Security and reliability fixes.

**Improvements**

- Usability improvements.
- Performance improvements.
- Quality-of-life changes.
- Balance adjustments.

**Additional Content**

- New features.
- New levels.
- Additional gameplay systems.
- Expansions or downloadable content.

**Project Closure**

- Final documentation.
- Repository maintenance.
- Archiving.
- Preservation of release artifacts.
- Final postmortem.

### 14.4. Expected Deliverables

Depending on the project's plans:

- Patches and updates.
- Updated release records.
- Defect reports.
- Player feedback analysis.
- Maintenance documentation.
- Postmortem.
- Project archive.

### 14.5. Exit Criteria

A project MAY be considered complete when:

- Planned post-release obligations are satisfied.
- No outstanding critical maintenance responsibility remains.
- Relevant project records are preserved.
- The project owner decides that active development has ended.

A completed project MAY still receive future maintenance or updates.

## 15. Lifecycle Stage Transitions

Lifecycle transitions SHOULD be based on evidence that the current stage has achieved its objectives.

### 15.1. Stage Reviews

At the end of a significant stage, review:

- Original objectives.
- Actual deliverables.
- Acceptance criteria.
- Outstanding work.
- Risks and dependencies.
- Quality and validation results.
- Readiness for the next stage.

### 15.2. Transition Decisions

A stage review SHOULD result in one of the following decisions:

- **Proceed:** The project is ready to enter the next stage.
- **Proceed with Conditions:** The project may advance while specific known issues or actions remain.
- **Continue:** Additional work is required within the current stage.
- **Reassess:** The project direction, scope, or approach requires review.
- **Pause:** Work is temporarily suspended.
- **Cancel:** The project or initiative is discontinued.

### 15.3. Conditional Progression

Projects MAY proceed with known incomplete work when the remaining issues do not invalidate the next stage.

Conditions MUST be documented and tracked.

Critical risks MUST NOT be ignored merely to preserve a schedule.

### 15.4. Iteration Between Stages

A project MAY return to an earlier stage when new evidence invalidates previous assumptions.

Examples:

- A prototype reveals that the core gameplay concept is not engaging.
- Production exposes a major technical limitation.
- Alpha testing identifies structural gameplay problems.
- Beta testing reveals significant progression issues.
- Release validation identifies unacceptable stability problems.

Returning to an earlier stage is a legitimate development decision, not automatically a project failure.

## 16. Project Planning and Tracking

Each project SHOULD maintain a lifecycle plan appropriate to its size.

### 16.1. Milestones

Major lifecycle stages SHOULD be represented through meaningful project milestones when milestone tracking is used.

Milestones SHOULD define:

- Intended outcome.
- Expected deliverables.
- Acceptance criteria.
- Dependencies.
- Risks.
- Target dates, when applicable.

### 16.2. Backlog

The project backlog SHOULD contain the work required to achieve lifecycle objectives.

Work items SHOULD be prioritized according to project value, risk, dependencies, and available capacity.

### 16.3. Progress Tracking

Project progress SHOULD be evaluated through:

- Completed deliverables.
- Demonstrable functionality.
- Validation results.
- Remaining work.
- Identified risks.
- Milestone outcomes.

Activity counts alone MUST NOT be treated as proof of meaningful progress.

### 16.4. Scope Changes

Changes to project scope SHOULD be evaluated against:

- Player experience.
- Project objectives.
- Available capacity.
- Technical impact.
- Production dependencies.
- Schedule and release impact.
- Quality risks.

Significant changes MUST be approved by the project owner and reflected in relevant project documentation.

## 17. Risk Management

Risks SHOULD be identified and reviewed throughout the project lifecycle.

Examples include:

- Unvalidated gameplay assumptions.
- Technical feasibility.
- Engine limitations.
- Performance constraints.
- Content production capacity.
- External dependencies.
- Licensing restrictions.
- Platform requirements.
- Scope growth.
- Schedule uncertainty.
- Data loss.
- Tooling limitations.

Significant risks SHOULD include:

- Description.
- Potential impact.
- Likelihood or uncertainty.
- Mitigation strategy.
- Responsible owner.
- Current status.

Risk management SHOULD focus on reducing uncertainty and preventing avoidable project failures.

## 18. Project Documentation

Each game project SHOULD maintain documentation appropriate to its development stage.

Documentation MAY include:

- Game design documents.
- Technical architecture documents.
- Architecture Decision Records.
- Feature specifications.
- Milestone plans.
- Backlog records.
- QA and testing documentation.
- Art and audio production documentation.
- Release documentation.
- Postmortems.

Project-specific documentation MUST follow the studio documentation standards.

The project repository SHOULD remain the authoritative location for project-specific lifecycle records.

## 19. Lifecycle Adaptation

The recommended lifecycle is not a rigid production model.

Projects MAY adapt it according to their scope, risks, and development approach.

### 19.1. Small Projects

Small projects MAY:

- Combine project initiation and concept development.
- Perform limited pre-production.
- Use short prototypes.
- Combine Alpha and Beta validation.
- Use simplified release preparation.
- Conduct concise postmortems.

### 19.2. Experimental Projects

Experimental projects MAY prioritize prototyping and validation before establishing a detailed production plan.

Their primary objective may be learning rather than producing a complete game.

### 19.3. Large or Complex Projects

Larger projects MAY require:

- More detailed stage plans.
- Additional milestones.
- Separate content and technical reviews.
- Formal risk assessments.
- More extensive QA activities.
- Platform-specific release validation.
- Dedicated post-release maintenance planning.

### 19.4. Iterative and Agile Development

Projects using Scrum, Kanban, or similar approaches SHOULD continue to use iterations within lifecycle stages.

Sprints do not replace lifecycle stages.

A project may complete multiple iterations of design, implementation, integration, and testing before satisfying a stage's exit criteria.

## 20. AI-Assisted Project Lifecycle Management

AI agents MAY assist with lifecycle activities.

They MAY:

- Draft project plans.
- Break objectives into backlog items.
- Prepare milestone proposals.
- Summarize project progress.
- Identify missing deliverables.
- Analyze risks and dependencies.
- Prepare stage review documentation.
- Compare planned and actual outcomes.
- Draft postmortems.
- Recommend process improvements.

AI agents MUST:

1. Follow approved project documentation.
2. Use actual repository and production evidence.
3. Distinguish verified progress from assumptions.
4. Report incomplete work honestly.
5. Identify uncertainty and unresolved risks.
6. Preserve approved project scope and decisions.
7. Update project records when authorized.
8. Request approval for significant scope or lifecycle changes.

AI agents MUST NOT:

- Declare a lifecycle stage complete without evidence.
- Invent deliverables or validation results.
- Approve releases.
- Independently cancel or redefine a project.
- Change major project objectives without approval.
- Mark milestones complete based only on generated reports.

The project owner retains responsibility for lifecycle decisions and approvals.

## 21. Lifecycle Review Checklist

Use the applicable items when reviewing a project or lifecycle transition.

### Project Direction

- [ ] Project objectives are documented.
- [ ] Intended player experience is understood.
- [ ] Scope is appropriate.
- [ ] Important assumptions are identified.

### Planning and Execution

- [ ] Current lifecycle stage is understood.
- [ ] Expected deliverables are defined.
- [ ] Milestones reflect meaningful outcomes.
- [ ] Backlog items support current objectives.
- [ ] Dependencies and risks are tracked.

### Quality

- [ ] Development standards are followed.
- [ ] Testing is integrated into development.
- [ ] Technical and content quality are evaluated.
- [ ] Known defects are documented.
- [ ] Validation results are available.

### Transition Readiness

- [ ] Current stage objectives are satisfied.
- [ ] Required deliverables are available.
- [ ] Acceptance criteria have been evaluated.
- [ ] Remaining work is understood.
- [ ] Risks are documented.
- [ ] The project owner has reviewed the transition decision.

### Project Records

- [ ] Relevant documentation is updated.
- [ ] Milestone records reflect actual outcomes.
- [ ] Important decisions are documented.
- [ ] Project history is preserved.

## 22. Exceptions

Projects MAY deviate from the recommended lifecycle when justified by:

- Project size.
- Experimental objectives.
- Technical constraints.
- Available resources.
- Development methodology.
- Distribution model.
- Specific production requirements.

Significant deviations SHOULD be documented.

Changes to studio-wide lifecycle standards require project owner approval.

## 24. Maintenance

These guidelines SHOULD be reviewed periodically and updated when:

- Studio production practices change.
- New development methodologies are adopted.
- Project lifecycle requirements evolve.
- Recurring production problems reveal process improvements.
- New tools or workflows materially affect project management.

Changes MUST preserve the distinction between reusable studio lifecycle practices and project-specific plans.

The project owner is responsible for approving changes to these guidelines.
